# Архитектура D&D Combat Tracker — рабочая спецификация v0.1

Статус: **рабочая, не финальная**. Цель — быстро реализовать demo-базу и проверить гипотезы тестами. Это не контракт на полную реализацию D&D 5e. Правила: **D&D 5e (2014)**.

## Принятые решения

| ADR | Решение |
| --- | --- |
| 001 | Combatant — локальный снимок боевых характеристик с необязательным внешним `characterId`. Связь с Character Service не требуется для проведения боя. |
| 002 | Предварительно: `Combat` — единый Aggregate Root, `Combatant` и `ConditionInstance` внутри него. Проверить на demo. |
| 003 | Строгий режим: система запрещает нарушение **реализованных** правил, но не симулирует всё D&D. |
| 004 | MVP: жизненный цикл, инициатива/ходы, HP, временные HP, спасброски от смерти и состояния. Без атак, заклинаний, карты, концентрации и экономики действий. |
| 005 | `deathPolicy` на каждом Combatant: `DEATH_SAVES` или `INSTANT_DEATH_AT_ZERO`. Предпочтительные начальные значения: PC → первое, обычный монстр → второе; NPC — уточнить, предлагаем второе. |
| 006 | Длительность состояния может зависеть от начала/конца конкретного наступления хода конкретного участника. |
| 007 | Источник истины — актуальное состояние в PostgreSQL, дополнительно append-only `combat_events`. **Не Event Sourcing**. |
| 008 | Все изменяющие команды имеют уникальный `commandId` и идемпотентны. |
| 009 | Самописная кольцевая `TurnQueue` с **индивидуальными** ходами; порядок хранится в `combatants.turn_position`. Отдельная таблица очереди не нужна. В `ACTIVE` разрешено добавлять новых участников; они получают первый ход только со следующего раунда независимо от инициативы. Порядок их ходов начиная со следующего раунда определяется обычными правилами инициативы. Детали хранения допуска к ходу и перестановки `turn_position` ещё подлежат проверке на demo. |
| 010 | Явные начало и конец хода; обязательная проверка может заблокировать завершение хода. |
| 011 | `ConditionInstance`: завершение по игровому моменту и/или разрешённому игровому условию; универсальный движок эффектов не входит в MVP. |

| 012 | Инициатива каждого Combatant рассчитывается при его создании и сохраняется в боевом снимке. Запуск Combat формирует порядок из уже готовых значений; повторный бросок при запуске не выполняется. Новому участнику ACTIVE инициатива известна при создании, а первый ход доступен только со следующего раунда. |

Все ADR выше зафиксированы как решения архитектурной сессии, кроме **предварительного** ADR-002. Детали схемы и реализации до проверки demo остаются изменяемыми.

## Домен

- **Combat**: `PREPARING → ACTIVE → FINISHED`; хранит раунд, текущий ход, версию агрегата. Добавление участников разрешено в `PREPARING` и `ACTIVE`, но запрещено в `FINISHED`. FINISHED — терминальное состояние; не завершаем бой автоматически по HP противников.
- **Combatant**: участник *этого* боя, собственный ID; необязательный `characterId`; тип (ENEMY/NPC/PARTY_MEMBER), HP, вычисленная при создании инициатива, lifeState, deathPolicy, death-save counters, surprise, счётчики начал/окончаний ходов. Способ создания зависит от типа (шаблон противника, ручной лист NPC, снимок персонажа).
- **TurnQueue**: сортирует по установленному порядку; у каждого включённого в очередь участника ровно одна уникальная позиция. После старта состав очереди может измениться при добавлении нового участника. При обходе погибших их позиции сохраняются, но **игровые ходы не создаются**. Умирающий участник ход получает для death save. Участник, добавленный во время `ACTIVE` в раунде N, не получает ход в этом раунде и впервые допускается к ходу с раунда N + 1. Инициатива определяет его позицию в порядке ходов начиная со следующего раунда. Положение текущего хода сохраняется. Способ хранения допуска к ходу и безопасной перенумерации `turn_position` ещё требуется определить.
- **ConditionInstance**: каждое наложение имеет независимую идентичность, источник, состояние ACTIVE/ENDED и основания окончания. Несколько одинаковых типов не складываются; эффективный тип действует, если остался активный источник. `Unconscious` от 0 HP — производное состояние, не самостоятельный экземпляр.
- **PendingResolution** (гипотеза): сохраняемая обязательная проверка, например death save в начале хода. Отдельная таблица рекомендована, но ещё не утверждена.
- **CombatEvent**: запись произошедшего доменного события. Не путать с интеграционными событиями Kafka.
- **ProcessedCommand**: регистрация commandId, типа/отпечатка запроса и результата для безопасных повторов.

## Базовые инварианты

1. Combatant и все его состояния принадлежат ровно одному Combat. Любая ссылка на участника в текущем ходе, условии истечения или проверке обязана указывать **на тот же бой**.
2. Каждый созданный Combatant имеет рассчитанное значение инициативы. ACTIVE требует непустого определённого порядка и текущего хода; первый раунд = 1. При запуске боя TurnQueue упорядочивает участников по готовой инициативе без нового броска. Запуск боя повторно запрещён.
3. Добавлять Combatant можно только в `PREPARING` или `ACTIVE`. В `ACTIVE` добавление не должно терять текущий ход, нарушать уникальность позиции в `TurnQueue` или выполнять повторно уже завершённые ходы. После `FINISHED` нельзя изменять боевое состояние. Первый ход добавленного в раунде N участника допустим только с N + 1, независимо от инициативы. Очередь не должна выбирать нового участника до этого раунда; при наступлении следующего раунда действует порядок инициативы. Конкретный способ хранения этого ограничения и перестановки позиций остаётся вопросом реализации.
4. HP: `maxHp > 0`, `0 ≤ currentHp ≤ maxHp`, `temporaryHp ≥ 0`. Временные HP поглощают урон первыми; источники временных HP не суммируются.
5. При 0 HP lifeState определяется правилами урона, выбранной deathPolicy, стабилизацией и особыми случаями. **0 HP ≠ обязательно DEAD**. Учесть мгновенную смерть от массивного урона и критический урон по существу на 0 HP.
6. Death saves: при DYING — в начале собственного хода; 10–19 успех, 2–9 провал, натуральная 1 — два провала, натуральная 20 — восстановление 1 HP; три успеха → STABLE, три провала → DEAD. При стабилизации или восстановлении HP счётчики обнуляются.
7. Начало/конец хода — логические атомарные этапы. При незавершённой обязательной проверке ход не завершается. Счётчики start/end увеличиваются **только при фактическом начале/конце хода**.
8. Истечение ConditionInstance по времени привязывается к наступлению конкретной фазы хода выбранного участника, а не только к номеру раунда. Если ход погибшего не наступил, его счётчики не меняются и условие не срабатывает само.
9. Успешная команда атомарно изменяет состояние, увеличивает версию агрегата, записывает события и результат идемпотентности. Конфликт конкурентных разных команд не должен автоматически выполнить команду ещё раз на новом ходе.
10. Создание одной команды с тем же commandId/тем же содержимым возвращает зафиксированный результат; тот же ID с иным содержимым — конфликт.

## Не включаем в demo

Групповые слоты инициативы; удаление участников из активного боя; произвольный пересчёт инициативы; автоматический расчёт атак/урона/спасбросков от эффектов; заклинания; перемещение; действия и реакции; концентрация; многоступенчатая Exhaustion; интеграция Character Service; Kafka/ClickHouse; Event Sourcing.

## Требующие проверки на работающей БД вопросы

- Нужна ли отдельная `pending_resolutions` в первой миграции, или хватит минимального контекста одной death save? В спецификации ниже предложена таблица.
- Как хранить альтернативные причины завершения ConditionInstance: одни nullable-поля для простого MVP или отдельные записи правил?
- Точный жизненный цикл `lifeState` при нокаутирующей атаке, повторном уроне на 0 HP, лечении и смерти. Не закладывать противоречащие правилам жёсткие CHECK до тестов.
- Как представлять «обязательный бросок начала хода» и порядок нескольких обязательных проверок.
- Как разрешать совпадения рассчитанной при создании инициативы при формировании и обновлении очереди, и как включать нового Combatant в `TurnQueue` при `ACTIVE`: инициатива и разрешение равенства инициатив, безопасное назначение/перенумерация `turn_position`, хранение признака допуска к ходу начиная с раунда N + 1 и поведение при добавлении во время START/END или незавершённой обязательной проверки. Сам момент первого допустимого хода уже утверждён: не раньше следующего раунда.
- Ретенция завершённых боёв/событий и ответы на повтор неуспешных команд.

См. [demo-database.md](demo-database.md). Следующий шаг — **минимальная Liquibase-схема в отдельном PR**, интеграционные тесты PostgreSQL Testcontainers, затем пересмотр спецификации по фактам. Не создавать объёмные доменные слои раньше этой проверки.
