# Независимое ревью PR

Используйте этот навык только по явному запросу пользователя проверить конкретный PR. Навык задаёт read-only процесс и не является отдельным автономным reviewer-агентом.

## Входные данные

- номер или URL PR;
- репозиторий, если он не следует из контекста;
- связанная Issue и дополнительные области внимания.

Перед ревью прочитайте `AGENTS.md`, Issue, описание PR, полный diff, изменённые тесты и необходимый окружающий код. Проверяйте актуальный SHA PR.

## Шаги

1. Сверьте diff с целью и критериями Issue, найдите изменения вне scope.
2. Проверьте корректность, обработку ошибок, безопасность данных, совместимость конфигурации и миграций.
3. Проверьте тесты: покрывают ли они новое поведение, негативные и граничные сценарии, PostgreSQL и повторные операции, где это применимо.
4. Для каждого замечания подтвердите конкретный путь выполнения или входные данные, которые приводят к дефекту. Не публикуйте предположительные замечания без воспроизводимого сценария.
5. Отсортируйте замечания по severity и укажите самый узкий полезный путь и строку. Предложите направление исправления, не переписывая PR самостоятельно.

## Severity

- `S1` — потеря данных, критическая уязвимость или неизбежный отказ основной функции.
- `S2` — существенный дефект, нарушающий критерий приёмки или обычный пользовательский сценарий.
- `S3` — ограниченный дефект или риск сопровождения с конкретным практическим последствием.
- `S4` — небольшое улучшение, не блокирующее принятие; не используйте для вкусовых предпочтений.

## Границы ответственности

- Режим строго read-only: не изменяйте файлы, ветки, PR, Issues или настройки репозитория.
- Не пушьте коммиты, не оставляйте approve/request changes, не выполняйте merge или auto-merge.
- Не запускайте разрушительные команды и не раскрывайте секреты.
- Если доказуемых дефектов нет, сообщите об этом прямо и перечислите остаточные риски или пробелы проверки.

## Выходной формат

Сначала перечислите замечания по убыванию severity. Для каждого укажите:

- `[S1–S4]` и краткий заголовок;
- конкретный сценарий дефекта и его влияние;
- путь и строку;
- предлагаемое направление исправления.

После замечаний укажите вопросы, остаточные риски и краткую сводку просмотренных областей. Не выносите решение о merge.
